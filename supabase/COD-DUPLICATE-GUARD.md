# Защита повторных заказов с оплатой при получении

Применено в продакшен 27 октября 2026 с разрешения пользователя: V2-миграция и деплой только `pay-v2`.

Одинаковые COD-заказы за последние 10 минут получают номер первой записи, даже если браузер прислал новый orderId. Сравниваются нормализованные телефон, имя, email, адрес, способ связи, комментарий, состав корзины (без зависимости от порядка строк), сумма и код промокода. Технические URL и новый orderId не участвуют. Карточные заказы не объединяются. Исторические заказы не удаляются.

Транзакционная advisory-блокировка в PostgreSQL сериализует одинаковые резервирования между экземплярами Edge Function. Дальнейшие отправки используют сохранённый номер и существующие блокировки Telegram по получателю. Пустого ответа или ошибки RPC нельзя обходить обычной вставкой: защита работает fail-closed.

Для включения после разрешения на деплой:

1. Применить только `supabase/migrations/20261027100100_v2_cod_duplicate_guard.sql` к активной V2-базе. Эта миграция не меняет legacy-таблицы, cron и существующие заказы.
2. Развернуть только `pay-v2` со связанным `_shared/order-store.mjs` и обновлённым `isolation.mjs`. Не запускать `deploy-pay-v2.mjs`: он предназначен для первоначального создания namespace.
3. Сверить опубликованные исходники и проверить доступность функции. Не отправлять покупательские или тестовые Telegram-сообщения без разрешения.

`20261027100000_cod_duplicate_guard.sql` — аналог для локальной canonical-схемы `le_orders`; на текущий продакшен с V2 применяется только V2-вариант выше. Перед будущим деплоем canonical `pay` нужен соответствующий canonical RPC.

Проверки:

```sh
node --test supabase/functions/pay/tests/*.test.mjs supabase/functions/pay-v2/*.test.mjs storefront/tests/order-store.test.mjs storefront/tests/cod-server.test.mjs
deno check --node-modules-dir=auto --no-lock supabase/functions/pay/index.ts supabase/functions/pay-v2/index.ts
```
